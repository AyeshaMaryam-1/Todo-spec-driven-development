# Todo Spec-Driven Development Constitution

## Core Principles

### I. Specification-First Development
Every feature starts with a clear, detailed specification before any implementation begins; Specifications must be testable, measurable, and agreed upon by stakeholders; No implementation without an approved spec - YAGNI principle applied to ensure minimal viable specifications.

### II. Test-Driven Development (NON-NEGOTIABLE)
TDD is mandatory: Tests written → Spec approved → Tests fail → Then implement; Red-Green-Refactor cycle strictly enforced; All code changes must be accompanied by appropriate tests covering acceptance criteria.

### III. Todo-Driven Implementation
Implementation follows a clear task breakdown with granular, actionable todos; Each todo maps to specific spec requirements; Todos must be testable and verifiable with clear acceptance criteria.

### IV. Small, Testable Changes
Prefer the smallest viable diff that meets requirements; Each change should be independently reviewable and testable; No unrelated modifications or refactoring in the same change unless directly supporting the feature.

### V. Explicit Error Handling and Documentation
All error paths and constraints must be explicitly documented and handled; Code must be self-documenting with clear comments for complex logic; Acceptance criteria must include explicit error scenarios.

### VI. Continuous Integration and Validation
All changes must pass through CI pipeline before merging; Automated validation ensures spec compliance; No breaking changes without proper migration plan.

## Development Standards

All code must follow established patterns and conventions from the existing codebase; Prefer clarity over cleverness; Maintain consistency with architectural patterns established in the project; Code reviews must verify compliance with all constitution principles.

## Development Workflow

Specifications must be created and approved before implementation using `/sp.specify`; Implementation follows the task breakdown generated by `/sp.tasks`; All changes are tracked through Prompt History Records (PHRs) using `/sp.phr`; Architectural decisions are documented using `/sp.adr` when significant.

## Governance

This constitution supersedes all other practices and must be followed for all development activities; Amendments require explicit documentation, approval, and migration plan; All PRs and reviews must verify compliance with constitution principles; Use CLAUDE.md for runtime development guidance and MCP tools for all information gathering.
